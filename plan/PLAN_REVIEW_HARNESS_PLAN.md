# 계획 리뷰 하네스 추가

## Context
지금은 기능 요청 → 계획 작성 → 사용자 확인 순서로만 진행해서, 계획의 누락이나 과설계를 사용자가 직접 잡아야 한다.
기능 요청이 오면 아래 순서로 진행되도록 **리뷰 전용 서브에이전트**와 **작업 규칙**을 추가한다.
1. 계획 작성 → `plan/`에 저장
2. 리뷰 에이전트 호출 → 수정 제안
3. 작성 에이전트(메인)가 제안을 검토해 반영하거나 거절
4. 사용자 확인 → "구현 시작" 요청이 오면 구현

강제 장치(hook)는 넣지 않는다. 서브에이전트 정의와 CLAUDE.md 규칙만으로 충분하다.

## 변경 1 — `.claude/agents/plan-reviewer.md` (신규)
Claude Code 프로젝트 서브에이전트로 만든다. 읽기 전용이며 계획 파일을 직접 고치지 않고 제안만 반환한다.
```markdown
---
name: plan-reviewer
description: plan/ 폴더의 구현 계획 문서를 리뷰하고 수정 제안을 반환한다. 계획 작성 직후 반드시 호출.
tools: Read, Grep, Glob
---
너는 이 저장소(wiki_collector: 단일 파일 tkinter 앱 `wiki_collector.py` + `test_wiki_collector.py`)의 구현 계획 리뷰어다.
입력으로 계획 파일 경로와 사용자 원래 요청을 받는다. 계획 파일은 수정하지 않는다.

확인 순서:
1. 계획과 계획이 언급한 코드/문서(`wiki_collector.py`, `README.md`, `doc/DECISIONS.md`, `doc/*prd*.md`)를 직접 읽는다.
2. 점검 항목
   - 요구 충족: 사용자 요청을 빠짐없이 다루는가
   - 범위 준수: 사용자가 요청한 기능에 필요한 수정만 하는가. 요청과 무관한 기존 코드 리팩토링(이름 변경, 구조 정리, 스타일 수정 등)이나 요청하지 않은 기능/코드 추가가 있으면 지적한다
   - 코드 정합성: 언급한 함수/설정 키/행 번호가 실제로 존재하는가, 재사용할 기존 함수를 놓쳤는가
   - 과설계: 불필요한 새 함수/파일/설정/추상화가 있는가
   - 예외 케이스: 기능 구현 시 생길 수 있는 예외 상황을 계획이 다루는가. 예) 빈 입력/공백만 있는 입력, 인코딩(cp949/UTF-8 BOM), 중복 파일명, 경로·파일명 금지문자, CLI 실패/timeout, 네트워크 오류, 설정 키 누락(기존 config.json 호환). 다루지 않은 예외는 처리 방법과 함께 제안한다
   - 위험: Windows 동작, 기존 config 호환, 기존 raw/ 데이터, 스레드/GUI 제약
   - 기존 결정과 충돌: `doc/DECISIONS.md`에 적힌 결정을 뒤집는가
   - 검증: 테스트 추가/수정과 수동 확인 방법이 구체적인가
3. 추측으로 지적하지 않는다. 근거가 되는 파일:줄을 적는다.

출력 형식(한국어):
## 리뷰 결과: <승인 가능 | 수정 필요>
| # | 등급 | 위치(계획 절) | 문제 | 근거 | 제안 |
등급: 필수(반영하지 않으면 버그/요구 누락/처리 안 된 예외, 요청 범위를 벗어난 수정) / 권장 / 선택
문제가 없으면 표 없이 "지적 사항 없음"과 확인한 항목만 적는다.
```

## 변경 2 — `CLAUDE.md`에 워크플로우 규칙 추가
기존 두 줄 아래에 추가한다.
```markdown
## 기능 구현 요청 시 워크플로우
1. 계획 작성: `plan/<주제>_PLAN.md`에 저장한다. plan mode라면 plan mode 파일에 쓰고, 승인 뒤 첫 단계로 `plan/`에 복사한다.
2. 리뷰: `plan-reviewer` 서브에이전트를 호출한다. 계획 파일 경로와 사용자 원래 요청을 그대로 넘긴다.
3. 반영: 제안마다 반영/미반영을 판단해 계획을 수정한다. 계획 끝에 `## 리뷰 반영` 절을 두고 제안별로 "반영" 또는 "미반영: 이유"를 적는다.
   - `필수` 제안을 거절하려면 이유를 반드시 적는다.
   - `필수` 제안을 반영하느라 계획이 크게 바뀌었으면 리뷰를 한 번 더 받는다(최대 2회).
4. 보고 후 대기: 수정된 계획 경로와 리뷰 반영 요약을 사용자에게 보여주고 멈춘다. 사용자가 구현 시작을 요청하기 전에는 코드를 수정하지 않는다.
```

## 변경 3 — 기록
- 이 계획을 `plan/PLAN_REVIEW_HARNESS_PLAN.md`로 복사한다(프로젝트 규칙).
- `doc/DECISIONS.md`에 절을 하나 추가한다: 리뷰 하네스는 서브에이전트와 CLAUDE.md 규칙으로만 구성하고 hook 강제는 넣지 않음, 리뷰는 최대 2회, 리뷰어는 읽기 전용.

## 검증
1. 새 세션을 연다(에이전트 정의는 세션 시작 시 로드된다). `/agents` 목록 또는 Agent 호출에서 `plan-reviewer`가 보이는지 확인한다.
2. 작은 기능 요청(예: "config에 X 옵션 추가해줘")으로 전체 흐름을 한 번 돌려 본다.
   - `plan/<주제>_PLAN.md` 생성 → `plan-reviewer` 호출 → 계획에 `## 리뷰 반영` 절 추가 → 코드는 수정하지 않고 멈추는지 확인한다.
3. 기존 `plan/MEETING_UPLOAD_PLAN.md`에 리뷰어만 단독으로 호출해 출력 형식과 파일:줄 근거가 제대로 나오는지 확인한다.

건너뛴 것: 리뷰를 강제하는 hook(예: ExitPlanMode 전에 리뷰 여부 검사). 규칙을 자주 빼먹으면 그때 추가한다.
